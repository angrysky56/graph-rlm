Standard Operating Procedure: Agentic Test-Driven Development (TDD) Systems1. OverviewThis document outlines the architectural standards for constructing autonomous software development systems that utilize Test-Driven Development (TDD). This approach transitions AI development from "Vibe Coding" (a human-centric, intuition-driven process) to "Agentic Coding" (a structured, autonomous execution model).The system described herein enforces the Red-Green-Refactor cycle through a multi-agent architecture, ensuring that code generation is verifiable, deterministic, and functionally accurate.2. Core PhilosophyTo ensure reliability in non-deterministic LLM systems, this framework adopts the Chicago School of TDD over the London School.Chicago School (State Verification): Agents verify behavior by asserting that specific inputs yield specific outputs (e.g., assert add(2,2) == 4). This is preferred for agents as it reduces hallucination risks associated with mocking complex interactions.Separation of Concerns: The cognitive load is distributed across specialized agents, preventing "God Tasks" where a single agent attempts to plan, code, and test simultaneously, which is a known failure mode.3. System Architecture: The TDD TriadThe system is composed of three specialized agents, each strictly scoped to a specific phase of the TDD cycle. These definitions follow the Role-Goal-Backstory framework.Agent A: The Test Architect (The "Red" Phase)This agent is responsible for defining the "Red" state (failure). It acts as the specifier and is strictly prohibited from writing implementation logic.AttributeSpecificationRoleSenior Test Automation Architect GoalTranslate functional requirements into failing unit tests that define expected behavior without implementing the logic.BackstoryYou are a veteran Quality Assurance engineer who strictly adheres to the "Chicago School" of TDD. You believe that implementation details are irrelevant until behavior is formally defined via a failing test. You specialize in state verification and edge-case identification.ToolsFile System Write Access (Restricted to ./tests/ directory).Agent B: The Implementation Engineer (The "Green" Phase)This agent is responsible for the "Green" state (passing). It operates under a "minimalist" constraint to prevent over-engineering.AttributeSpecificationRolePragmatic Python Systems Engineer GoalWrite the minimum code necessary to resolve the current test failure. Do not anticipate future requirements or optimize prematurely.BackstoryYou are a pragmatic developer who treats the test suite as the absolute source of truth. If the test suite does not require a feature, you do not build it. You rely exclusively on the execution logs provided by the pipeline to guide your syntax and logic corrections. ToolsFile System Write Access (Restricted to ./src/ directory); File System Read Access.Agent C: The Pipeline Operator (The Execution Phase)This agent serves as the runtime environment and objective judge. It bridges the gap between the agents and the execution sandbox.AttributeSpecificationRoleCI/CD Pipeline Operator GoalExecute test suites in a sandboxed environment, capture standard error (stderr) streams, and classify results as 'PASS' or 'FAIL'.BackstoryYou are an automated system operator with no opinion on code style, only on execution status. You are responsible for providing precise error logs to the Implementation Engineer to facilitate debugging. ToolsPytest Runner, Linter (e.g., Flake8), Sandbox/Docker Execution Tool.4. Operational Workflow (The Chat Chain)The agents interact through a structured "Chat Chain" or control loop that enforces the TDD cycle.Phase 1: Specification (Red)Input: A functional requirement (e.g., "Implement a class to handle user authentication").Action: The Test Architect generates a strictly failing test file (e.g., test_auth.py).Verification: The Pipeline Operator runs the test. The process only proceeds if the test fails (confirming the test is valid and detecting the missing feature).Phase 2: Implementation Loop (Green)Input: The content of the failing test file and the raw error logs from the Pipeline Operator.Action: The Implementation Engineer generates or modifies the source code (e.g., auth.py) to resolve the specific error found in the logs (e.g., ImportError, AssertionError).Verification: The Pipeline Operator runs the test again.If Fail: The logs are fed back to the Implementation Engineer (Self-Correction Loop).If Pass: The cycle is complete, or moves to refactoring.5. Task TemplatesTo ensure consistent execution, tasks must be defined with clear inputs and expected outputs, adhering to the "Single Purpose, Single Output" principle.Task Template: Spec CreationAssignee: Test ArchitectDescription: "Analyze the following feature request: {feature_request}. Create a Python test file that asserts the expected output for valid inputs and handles edge cases. The test MUST fail against an empty implementation." Expected Output: "A valid .py file stored in the tests/ directory containing at least three distinct test cases (Happy Path, Edge Case, Error Handling)." Task Template: Code ResolutionAssignee: Implementation EngineerDescription: "Review the failing test file {test_file_path} and the following error log: {error_log}. Write or modify the implementation file to resolve this specific error. Do NOT modify the test file." Expected Output: "A valid .py file stored in the src/ directory that causes the provided test to pass." 6. Implementation NotesSandboxing: Execution must occur in a secure, isolated environment (e.g., Docker) to prevent agents from modifying the host system or accessing unauthorized data.Log Parsing: The system must be capable of capturing stderr (standard error) output and feeding it back into the prompt context for the Implementation Engineer. This "feedback loop" is the defining characteristic of Agentic Coding.
